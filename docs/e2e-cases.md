# 画面 E2E テストケース

Playwright の **断言するケースの正**。実装は本ファイルの ID と 1 対 1。不足があればテストを足す前に本ファイル（必要なら [ui-spec.md](ui-spec.md) / [er.md](er.md)）を直す。

画面の正は [ui-spec.md](ui-spec.md)。表の正は [er.md](er.md)。権限行列は [test-cases.md](test-cases.md)（pgTAP）。計算は [calc-cases.md](calc-cases.md)（Vitest）。本ファイルはそれらを再実装しない。

Playwright は `web/e2e/*.spec.ts`。テスト名に本ファイルの ID を含める。

---

## 観点

1. **各テーブルに少なくとも 1 行できるパターンを通す**（画面から作れるもの。trigger のみの表は副作用として通る）
2. **通常画面を少なくとも一度表示する**（[ui-spec.md の画面一覧](ui-spec.md#画面一覧)。エラーダイアログ等は除く）

---

## この文書の読み方

| 列 | 意味 |
|----|------|
| ID | Playwright が実行するキー。実装で変えない |
| 対象 | 認証 / プロフィール / 麻雀グループ / 大会 / 試合 |
| 操作 | 開く・作る・保存する |
| 通す画面 | ヘッダーが見えれば表示したと数える |
| 通す表 | その操作で INSERT されるアプリ表。既にある行の UPDATE だけなら書かない |
| 期待 | 見出し・遷移先・保存後に見える名前 |

同一ルートのステップ（アカウント作成の OAuth 初画面とメール登録など）は、どちらも通常画面として一度は出す。

---

## 切り出す範囲

| やる | やらない |
|------|----------|
| ui-spec の通常画面を 1 回以上表示 | 見つかりません（`not-found`） |
| アプリ表へ 1 行以上入る成功経路 | 確認ダイアログ（削除・退会・離脱・素点合計のずれ・同名ルール・表示名未設定） |
| 作成中と保存後でルートが分かれる画面は両方 | 権限行列、他グループのデータ、OAuth プロバイダ画面 |
| ヘッダーと、作った名前が一覧または詳細に出ること | 全ボタンクリック、ピクセル一致、計算の数値そのもの |

`activity_logs` は UI に出ない。業務表への INSERT の trigger で増えるので、画面では断言しない。`auth.users` はアプリ表ではない。墓石（退会）は確認ダイアログを踏むため対象外。

表示の成功は **見出し（`h1` / `AppHeader` のタイトル）が見える**こと。インラインの未入力エラーを意図して出さない。出ても、見出しが見えていれば失敗にしない。

## フィクスチャ

| 名前 | 内容 |
|------|------|
| **e2e ユーザー** | メールログインできる利用中プロフィール。`profiles` の 1 行目は Auth 登録（global-setup 可）。毎回アカウント作成画面から登録しなくてよい |
| **操作対象の麻雀グループ** | ケース内で画面から作る（E-12）か、setup で空の所属グループだけ用意する。既定ルール・大会・試合・招待コードは **画面から** 足す |

global-setup が既定ルールまで API で入れている場合、差し替え時に外す（画面経路が setup に隠れるため）。

書き込みケースは実行ごとに一意な名前（タイムスタンプ等）を使う。ケース同士は独立してよい。通し（同じグループを E-12 から E-18 まで使う）でも、カバレッジ表を満たせばよい。

## テーブルカバレッジ

| テーブル | 入る経路 | ケース |
|----------|----------|--------|
| `profiles` | Auth 登録（setup 可）。画面は編集を表示する | E-10（表示）。INSERT は setup |
| `communities` | 麻雀グループを作成する | E-12 |
| `community_memberships` | 作成時に自分が入る | E-12 |
| `community_rules` | 既定ルールを追加する | E-13 |
| `community_invite_codes` | 招待で「発行する」 | E-14 |
| `tournaments` | 大会を作成する | E-15 |
| `tournament_rules` | 大会作成時に既定からコピーされる。不足なら保存後に追加 | E-15（コピー）。E-16 は画面 |
| `tournament_participants` | 保存後にメンバー 1 人とゲスト 3 人 | E-16 |
| `matches` | 試合結果を追加する | E-17 |
| `match_results` | 試合追加と同時（四麻 4 行） | E-17 |
| `tournament_point_adjustments` | ポイントの補正を保存する | E-18 |
| `activity_logs` | 上の INSERT の trigger。画面では断言しない | （副作用） |

招待コードで **別ユーザーが参加する** 経路は、2 人目が要るので本ケースに含めない（メンバーシップの 1 行は E-12 で足りる）。

### 麻雀グループ

| ID | 対象 | 操作 | 通す画面 | 通す表 | 期待 |

| E-12 | 麻雀グループ | 作成 → 詳細 → 編集を開く | 作成、詳細、編集 | `communities`, `community_memberships` | 一意な名前で「作成する」。詳細の見出しがその名前。編集の見出し「麻雀グループを編集」。「この麻雀グループを抜ける」は押さない |

### 大会

前提: 操作対象グループに既定ルールが 1 件以上ある（E-13）。

| ID | 対象 | 操作 | 通す画面 | 通す表 | 期待 |
|----|------|------|----------|--------|------|
| E-15 | 大会 | 大会作成を開き、作成中の参加者・ゲスト・ルール（選択とフォーム）を開いて戻る。名前を入れて「作成する」 | 大会作成、作成中の参加者／ゲスト／ルール選択／ルールフォーム、大会詳細 | `tournaments`。既定があれば `tournament_rules`（コピー） | 各見出し。作成後に大会名の詳細。作成中の追加画面では保存しなくてよい（戻るだけで表示） |
| E-16 | 大会 | 詳細から編集。参加者に自分を追加。ゲストを 3 人追加。ルール追加（選択とフォーム）を開く。ルール行から詳細を開く | 大会編集、保存後の参加者／ゲスト／ルール選択／ルールフォーム、大会ルール詳細 | `tournament_participants`（メンバー 1＋ゲスト 3） | 編集の見出し。追加後に名前が見える。ルール詳細の見出し。フォームでは「追加する」を押さなくてよい（コピーは E-15 で済む） |
| E-18 | 補正 | 大会詳細からポイントの補正を開き、列タイトルと 1 人分の値を入れて保存する | ポイントの補正 | `tournament_point_adjustments` | 見出し「ポイントの補正」。保存後は大会詳細へ戻るので、補正画面を開き直して入れたタイトルまたは値が見える |

E-15 で既定ルールがコピーされない（0 件のまま作成した）ときは、E-16 のフォームで大会ルールを 1 件追加して `tournament_rules` を満たす。

ゲスト 3 人は四麻の試合（E-17）用。表示名は一意でなくてよい（同名警告のダイアログは踏まない）。

### 試合

前提: 大会にルール 1 件以上、参加者 4 人（自分＋ゲスト 3）。

| ID | 対象 | 操作 | 通す画面 | 通す表 | 期待 |
|----|------|------|----------|--------|------|
| E-17 | 試合 | 試合一覧から追加。東＝自分、南・西・北＝ゲスト。素点 35000 / 25000 / 25000 / 15000。「追加する」。詳細から修正を開く | 試合作成、試合詳細、試合編集 | `matches`, `match_results` | 作成の見出し「試合結果を追加」。詳細は `#1`（その大会の最初なら）。編集の見出し「試合を編集」。「保存する」「この試合を削除する」は押さなくてよい |

素点合計は持ち点×人数と一致させる（確認ダイアログを出さない）。反映ポイントの数値は Vitest の範囲なので、詳細に自分の表示名が見えればよい。

## Playwright との対応

| 置き場所 | コマンド | CI |
|----------|----------|-----|
| `web/e2e/` | `web/` で `npm run test:e2e` | 既存 `e2e` job（ローカル Supabase が要る） |

1 ID = 1 `test()` が望ましい。E-15〜E-18 のように前の行が前提になるときは、`test.describe.serial` で 1 ファイルにまとめてよい（ID をテスト名に含める）。

権限・計算・ピクセルは他層。本ケースが赤なら画面の到達または成功経路が欠けている。
